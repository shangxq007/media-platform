# Test execution parallelization and validation policy V1

`governance/TEST_EXECUTION_TOPOLOGY_LEDGER.tsv` is the tracked authority for every active Gradle `Test` task. The policy applies `maxParallelForks` per task, not as a global JUnit or high-fork switch. Its exact classification vocabulary is `PURE_PARALLEL_SAFE`, `SPRING_HEAVY_BOUNDED`, `SERIAL_ONLY`, and `REVIEW_REQUIRED`.

The authoritative census contains 51 exact active `Test` task paths, including the realized `:platform-algorithms:test` parent task alongside `:platform-algorithms:graph:test`. Its zero discovered tests are not parallel-safe evidence, so it remains `REVIEW_REQUIRED` with one fork. The zero-test addition does not change the raw full-suite universe (`8209`) or topology gross count (`8215`).

`PURE_PARALLEL_SAFE` is a promotion, not a review assertion. The original21-task enrollment is retained as historical provenance, not a current all-pure claim. The current topology and enrollment suspend9 scopes with observed controlled-PG tests or Spring contexts: Worker Fabric, Artifact, Entitlement, Audit Compliance, Federation Query, Identity Access, Outbox, Payment and Timeline. They use one fork and `SUSPENDED_SOURCE_CHANGED`; the remaining12 historical sealed scopes retain their existing classification and are not newly certified here. Both evidence columns retain the tracked `governance/TEST_EXECUTION_PARALLELIZATION_PROMOTION_RECEIPT_V1.tsv`. The static validator accepts no arbitrary `evidence/...` prefix: it requires that exact receipt and verifies its complete contents, including the external report filenames and SHA-256 values. Missing, substituted, or changed receipt bytes fail closed. `SPRING_HEAVY_BOUNDED` is the positive Spring-context class and is capped at `maxParallelForks=1`; it is used for billing, notification, datasource, and Spring worker tasks unless a concrete exclusive resource requires `SERIAL_ONLY`. `REVIEW_REQUIRED` and `SERIAL_ONLY` are both capped at one; every serial-only task has a matching non-blank entry in `TEST_EXECUTION_SERIAL_ONLY_LEDGER.tsv`.

The root Gradle policy sets `junit.jupiter.execution.parallel.enabled=false` for every test task. It intentionally does not enable global JUnit intra-JVM parallelism, use a global 16/32/80 fork value, or make a module-wide assertion stronger than the task boundary permits. `platform-app` is capped at one fork. Gradle mechanically creates two phases: only `PURE_PARALLEL_SAFE` and `SPRING_HEAVY_BOUNDED` tasks can participate in the module-level parallel phase; all `REVIEW_REQUIRED` and `SERIAL_ONLY` tasks wait for that phase and are chained with `mustRunAfter`, so restricted tasks cannot overlap even under `--parallel`.

The default Gradle profile consumes the current topology: only currently sealed pure tasks use two JVM forks; suspended, Spring and restricted tasks use one. Global JUnit intra-JVM parallelism remains disabled. The historical Hermes result does not certify changed task scopes. `-PtestExecutionCandidateProfile=true` remains an opt-in only for future `CANDIDATE_ONLY` enrollment. It overlays only unsealed review-required rows, so it is a no-op for these sealed rows and cannot double-promote them.

The runner requires a frozen wrapper command containing `-PtestExecutionCandidateProfile=true`, `--rerun-tasks`, and `test`, and appends exactly one `--parallel --max-workers=N` profile per run. It requires external report, per-run output, and raw expected-universe paths. ## Ledger column semantics

This section is normative for the `TEST_EXECUTION_TOPOLOGY_LEDGER.tsv` columns it names. It defines field semantics; the separately recorded scope corrections in the current ledgers suspend unproven promotions without changing historical promotion receipt bytes. `audit-runs/FONT_V1_PHASE2_20261004/GOVERNANCE_PROBE.md` is historical probe evidence and is **not** the normative source for field semantics; where it and this section differ, this section governs the named columns.

- `USES_TESTCONTAINERS` — `YES`/`NO`. `YES` means the Gradle `Test` task's actual test scope contains a test execution path that requires Testcontainers. `NO` means the task's actual test scope does not use Testcontainers. A module-level dependency, a container base class present only in test fixtures, or test classes outside the task's selected scope are **not** sufficient on their own to justify `YES`. A record whose test scope cannot be confirmed against the task definition keeps its current value and is reported as evidence-insufficient.
- `USES_DOCKER` — `YES`/`NO` (definition D1). `YES` means the task requires a Docker-compatible container daemon/API; a Podman or other equivalent runtime that satisfies the compatibility requirement counts. `NO` means the task requires no such container daemon/API. This column records an infrastructure dependency and does not assert that a given execution connected to a specific runtime; the presence of Testcontainers is not by itself proof of runtime behaviour, so the value is judged from the task scope, the relevant test paths and the known runtime configuration.
- `KNOWN_SHARED_EXTERNAL_RESOURCE` — a single named token, or `NO` (definition S2). A token records a shared external resource for which there is evidence of sharing across test classes, tasks, forks, the host or the container runtime. New tokens carry a resource-category prefix (`RUNTIME_`, `DATABASE_`, `SERVICE_`, `FILESYSTEM_`, `CONTEXT_`); existing tokens (for example `SPRING_*`, `TEMPORAL_*`, `FONT_*`, `JOOQ_*`, `BUBBLEWRAP_CONTAINER_SANDBOX`, `*_REVIEW_PENDING`) remain valid. An independently created per-fork PostgreSQL container must **not** be recorded as a shared database, and a shared Podman runtime must **not** be recorded as a shared database. `NO` means no confirmed shared external resource applies to the task; it does not prove the task is parallel-safe, and a token does not by itself imply data contamination, resource contention or a ban on parallelism. The column stays single-valued with no new delimiter syntax; when several candidate resources exist, record the single most significant evidence-backed token and report the rest outside the ledger.
- `USES_DATABASE` — `YES`/`NO`. `YES` means the task's actual test scope touches a database through migrations, queries or writes; whether that database is provided by a Testcontainers instance is irrelevant to this column.


## Current controlled PostgreSQL scope

The historical sealed receipt and its 8094/8209/8215 counts describe their original source cohort; they are not proof of the current PG18 test inventory or current parallel safety. `DISCOVERED_TEST_COUNT` remains the historical ledger census until a fresh full discovery replaces it. Current acceptance uses exact source-bound JUnit identities and pass/fail/skip arithmetic, recorded by the actual run. No historical receipt may promote a changed database scope.

The9 suspended scopes have controlled PG18 tests or Spring contexts, as recorded by their current task-wide source. Provisioning for controlled PG18 belongs to the separate protected developer entry; that does not make a database-consuming task pure or give it Docker access. Their old pure-suite promotions are suspended, canonical fork limits are one, and the benchmark candidate overlay cannot re-enable them. Database cases require class-owned schemas and controlled credentials; no PG15/public-schema or shared-fixture assumption authorizes concurrency. A future promotion needs a fresh complete scope census and collision-free execution evidence for that exact source. Other unchanged sealed cohorts are not re-certified by this task.
