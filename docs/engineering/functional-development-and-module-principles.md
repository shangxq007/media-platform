# Media Platform — 功能驱动开发与模块架构原则

本文件是日常架构设计、功能开发、模块重构和 Agent 执行任务的默认工程总则。
它指导如何完成工程工作，不授予修改代码、数据库、资源或 Git 历史的权限。
任务授权、安全和工具约束遵循根 [AGENTS.md](../../AGENTS.md)；领域语义遵循有效的
Owner 决定、已采纳 ADR 和正式公开契约，不以本指南另建领域权威。

## 功能与验证

1. **从功能开始。** 先明确用户可观察的行为、输入输出、失败语义和验收路径，再判断需要哪些模块或接口。
   不为假想的未来场景预建通用框架、抽象层或治理流程。
2. **真实闭环优先。** 优先完成有边界的业务闭环，直接解决阻碍它的相关根因；
   不以无必要的提前治理拖延功能，也不以临时打通为由破坏安全或领域契约。
3. **用运行结果验证架构。** 编译、模块图或 Fake 通过不能代替真实集成行为。
   验证必须与任务授权匹配：文档任务只核查文档和范围；需要真实运行却尚未执行的部分如实保留未验证状态。
4. **测试维护真实正确性。** 覆盖成功、失败、重试、隔离及副作用；不得删去有效业务场景、弱化断言、
   Mock 正式结果或跳过安全检查来制造通过。重组测试时说明旧场景到新测试的等效关系。

## 模块与权威

5. **高内聚、低耦合。** 明确每个模块的数据和状态写入 Owner、公开能力、依赖方向及失败边界。
   跨模块调用使用正式公开契约，不依赖对方内部 Repository、持久化实体或实现类。
6. **复用既有能力。** 增加抽象前检查现有公开契约；不为每个调用机械增加 Port、转发层或重复 DTO。
   不把具体实现散播到 shared-kernel，也不让 platform-app 或应用协调层成为业务超级模块。
7. **保持单一领域权威。** 规划、Provider 选择、执行、Artifact 提交和领域终态各由其 Owner 负责。
   集成、验证探针和外部执行后端不得建立第二套状态机、提交权威或规划体系。

## 演进与执行

8. **不维护不存在的生产历史。** 项目尚未上线，不为错误中间状态保留无意义兼容层。
   数据库阶段政策统一见 [Flyway 基线](../database/flyway-migration-baseline.md)，不在这里另建迁移规则。
9. **允许有证据、有范围的整理。** 可以在已授权范围内删除、合并或重构错误、重复和过时实现，
   同步维护有效文档与测试；旧蓝图和类结构不是目的。删除前确认用途与归属，不把“未上线”解释为可丢弃现有工作或资源。
10. **保护工作并线性推进。** 先核对基线、脏修改与已有成果，围绕当前目标完成实现、验证和交付。
    普通修复按已有授权推进；遇到真实权限、资源、安全不变量或未决正式契约冲突，停止受影响操作并报告。
    不自行开始无关重构、并行功能任务、部署、提交或集成。
